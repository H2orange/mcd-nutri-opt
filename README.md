# 麦麦最优解 McdNutriOpt

> 输入「30 块 / 900 大卡 / 蛋白 30g」，输出帕累托最优的麦麦组合。
> 基于[麦当劳 MCP](https://github.com/M-China/mcd-mcp-server) 的约束求解型点餐助手。

**不是让大模型推荐，而是真的解数学题。** 求解器是纯本地计算，无 LLM 调用，可单元测试、结果可复现。

---

## 为什么做这个

健身和吃麦当劳是对立的。打开 App 想知道"今天 30 块能吃到多少蛋白"，得自己翻菜单、比价格、算热量——没人愿意。

现有的"推荐助手"都是提示词工程。这里换个思路：**这是一个多约束优化问题**。

```
输入：预算上限、热量上限、蛋白下限、忌口
目标：在满足所有约束的前提下，最便宜 / 蛋白最高
```

## 实测效果

以南京新百门店（`1990346`）2026-10 实测数据为例，约束「60 元 / 1500 kcal / 蛋白≥55g」：

| 指标 | 数值 |
|---|---|
| 菜单商品编码 | 83 |
| 营养对齐命中率 | **79%** |
| 枚举组合 | 83,820 |
| 可行解 | 1,862 |
| 帕累托前沿 | 12 |
| 求解耗时 | 126 ms |

```
42 元 | 932 kcal | 蛋白 56 g | 蛋白密度 1.3 g/元
  双层猪柳蛋麦满分 + 原味板烧鸡腿炒双蛋堡组合
```

对比同一天同一门店的严格品类去重模式（52.9 元 / 蛋白 55 g），**本项目自动选择了更优解**
并标注了策略来源。

## 三个技术要点

### 1. 菜单与营养表的语义鸿沟：命中率 15% → 79%

实测发现，门店菜单里**只有少数是营养表收录的传统单品**，其余是套餐、联名新品、酱料和周边。
直接按名称匹配命中率仅 15%。

采用四级降级链：

| 级别 | 策略 | 实测占比 |
|---|---|---|
| L1 | 名称精确匹配（归一化后） | ~35% |
| L2 | 双向包含，取最长匹配 | ~5% |
| L3 | **套餐拆解**：按 `rounds[].choices[].isDefault===1` 叠加子项营养 | ~40% |
| L4 | 剔除非食品（酱料/周边） | ~2% |

L3 是关键。MCP Server 的 `query-meal-detail` 已经标注了每个套餐的默认搭配，
所以拆解是精确的，不需要猜测。

### 2. 帕累托前沿，不是单点最优

「同等蛋白最少花多少钱」和「同等价格最多蛋白」是两个目标。
求解器枚举组合后计算帕累托前沿（价格↓ 蛋白↑的非支配解集），
输出完整权衡曲线，让用户自己选，而不是替他决定。

### 3. 品类槽位去重

套餐会展开成子项品类：「人气经典随心配」= 双层吉士汉堡 + 可乐麦炫酷，
占用了 `burger` 和 `drink` 两个槽位。若再单点一个汉堡，就是重复消费。

求解器感知这一点做冲突剪枝。但**严格模式会错过更优解**（某套餐已含汉堡后，
再无法搭配任何汉堡类高蛋白单品），因此**两种模式都跑，自动取优并标注策略来源**。

## 快速开始

### 离线体验（无需 Token）

```bash
git clone https://github.com/H2orange/mcd-nutri-opt
cd mcd-nutri-opt
npm run demo
```

内置 158 条营养数据（来自 `list-nutrition-foods`）与实测示例价格，clone 即可运行。

```bash
# 预算 30、热量 900、蛋白至少 30g
node src/cli.mjs --budget 30 --kcal 900 --protein 30

# 排除整个汉堡品类（会自动命中"板烧鸡腿堡"这类不含"汉堡"二字的命名）
node src/cli.mjs --budget 30 --protein 20 --exclude 汉堡

# 查看求解策略说明
node src/cli.mjs --budget 30 --kcal 900 --protein 30 --explain
```

### 在线模式（真实门店数据与价格）

```bash
#1. 申请 Token：https://open.mcd.cn/mcp
echo "你的TOKEN" > .env

node src/cli.mjs --live --city 南京 --keyword 新街口 --budget 60 --kcal 1500 --protein 55
```

在线模式会拉取真实门店菜单、逐个探测真实到手价（受 600 次/分钟限流约束），
结果缓存 6 小时。

### 运行测试

```bash
node --test "test/solver.test.mjs"
```

24 个用例，覆盖营养解析、帕累托前沿、求解器不变量、优惠分摊、四级降级对齐。

## 命令行参数

| 参数 | 说明 | 示例 |
|---|---|---|
| `--budget` | 预算上限（元） | `--budget 30` |
| `--kcal` | 热量上限（kcal） | `--kcal 900` |
| `--protein` | 蛋白下限（g） | `--protein 30` |
| `--sodium` | 钠上限（mg） | `--sodium 2000` |
| `--maxitems` | 最单品类数，默认 6 | `--maxitems 4` |
| `--exclude` | 排除关键词，逗号分隔，支持品类同义词 | `--exclude 汉堡,酱料` |
| `--only` | 白名单关键词 | `--only 麦满分` |
| `--live` | 在线模式 | `--live` |
| `--city` / `--keyword` | 门店定位（配合 `--live`） | `--city 南京 --keyword 新街口` |
| `--limit` | 价格探测抽样上限 | `--limit 30` |

## 目标用户

- **健身人群**：需要知道具体吃多少蛋白能达标，而不是模糊的"低卡推荐"
- **控制预算的人**：想用最少的钱达到营养目标
- **麦麦重度用户**：熟悉菜单但懒得翻 83 个商品比较

## 设计取舍

**为什么求解器不调 LLM？**
可测试、可复现、零延迟、无幻觉风险。LLM 适合生成文本，不适合做数值优化。

**为什么内置营养数据而不是每次实时拉？**
陌生人 clone 后 `npm run demo` 就能看到结果，不需要 MCP Token。
这是 Star 转化的关键——没人愿意为了看个 README 先去申请 Token。

**为什么缓存 TTL 是 6 小时？**
门店菜单按早市/午市/夜市切换，营业时间与价格相对稳定。
既避免频繁触发限流，又不至于拿到隔夜菜单。

**为什么对 L3-partial 结果显示警告？**
部分解析的套餐营养值是已解析子项之和，可能偏低。
藏起来会让用户误以为数据是精确的，这比给个差结果更糟。
