# 核心难点：菜单与营养数据的语义鸿沟

## 问题现象

实测门店 `1990346`（南京新百），122 个商品编码：

| 类别 | 数量 | 能直接匹配营养表？ |
|---|---|---|
| 传统单品（麦辣鸡腿汉堡、板烧鸡腿堡、麦香鸡…） | 少数 | ✅ 能 |
| 套餐（三件套/ 四件套 / 双件套 / 随心配） | 15+ | ❌ 不能 |
| 联名新品（龙焰系列、韩式系列） | 大量 | ❌ 不能 |
| 酱料、周边（酱料、汉堡帽） | 若干 | ❌ 无营养意义 |

**直接按名称匹配的命中率仅约 15%**（9/60抽样）。

## 根本原因

三个数据源的口径不一致：

1. **营养表**（`list-nutrition-foods`）：按**单个标准单品**收录，共 158 条，是全球统一标准值，不含套餐、不含限定新品。
2. **门店菜单**（`query-meals`）：是**当前门店在售**的全部商品，含大量套餐组合与地区限定新品。
3. 菜单里还有**非食品类**商品（酱料、联名周边），根本不该进营养计算。

所以「菜单 ×营养表」不是简单的一对一join，而是需要**语义对齐**。

## 解决思路（分四级降级）

### L1 精确匹配
名称完全一致（归一化去空格/括号后）→ 直接取营养值。

### L2 包含匹配
菜单名包含营养表名，或反之。例如：
- 菜单 `麦辣鸡腿堡` → 营养表 `麦辣鸡腿堡` ✅
- 菜单 `板烧鸡腿堡` → 营养表 `原味板烧鸡腿堡`（需去掉「原味」前缀做二次匹配）

实现：双向 `includes`，取**最长匹配**（避免「麦香鸡」误配「麦香鱼」）。

### L3 套餐拆解
套餐名形如 `X三件套` / `X四件套` / `X + Y 组合`，且 `query-meal-detail` 返回的 `rounds` 字段含子项。

**实测确认**：`1440`（麦辣鸡腿汉堡单品）的 `rounds` 为 `[]`，而套餐类商品的 `rounds` 有值，结构为：

```json
{
  "rounds": [
    { "code": "...", "name": "...", "items": [ { "code": "9900016075", "name": "..." } ] }
  ]
}
```

拆解策略：套餐营养 = Σ 子项营养 × 数量。
子项若能匹配营养表则叠加，匹配不到的**按套餐总价与已知子项做比例分配**（兜底估算）。

### L4 剔除不可算项
- 名称含「酱」「包」「帽」「杯套」「玩具」等→ 标记为 `nonFood`，不进营养计算
- 营养数据全为 0 且名称疑似饮料 → 单独标记 `zeroCalorie`（如无糖可乐真实就是 0 热量，不能剔除）

## 为什么不干脆只按营养表求解？

只在内置营养表上求解，会丢失「门店真实在售与价格」这个最有价值的维度——用户能在本项目里查到的价格必须是他附近门店真能买到的。所以必须走 L1–L4 的降级链，而不是回避菜单。

## 命中率提升的验证口径

`--live` 模式下需输出 `matched / total` 与 `breakdown`（各级别命中数），作为可观测指标。目标：L1+L2 命中率 ≥ 40%（把套餐拆解计入后 ≥ 70%）。
